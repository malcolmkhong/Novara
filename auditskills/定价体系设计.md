## 0. 结论先行

1. **计量链条已经建成一半**：token → USD → credit 的换算在代码里已存在且规则清晰（1 credit = $0.001 实测 AI 成本）。缺的是 **credit → 套餐** 这一段：订阅状态、套餐含积分额度、超量购买、权益强制执行。
2. **产品原型判定：Copilot 为主**（AI 辅助作者写作，人在审批环内）→ 按人订阅 + 积分用量是正确的混合模式，现有 Free/Creator/Studio 三档结构方向正确。
3. **核心设计决策（建议）**：套餐月费含固定积分额度（Base + credits 混合模式），"月 AI 字数"降级为宣传口径；超量按积分包购买，单价为成本的 1.2–2 倍。
4. **当前最大风险不是定价，是成本口径**：注册表价格全部标注 UNVERIFIED，且缓存折扣不可见导致成本只是上界估计——定价前必须先把模型单价核实。

## 2. Token 层：成本怎么算

### 2.1 已实现的规则【已实现】

- 唯一价格表：`src/lib/usage/pricing.ts`，版本号 `PRICING_VERSION = "2026-11-06.1"`，按请求侧 modelId 键控。
- 公式：`USD = (promptTokens × inputUsdPer1M + completionTokens × outputUsdPer1M) ÷ 1,000,000`
- **诚实规则（代码注释中的绑定约束）**：
  1. 所有金额 = 实测 tokens × 表列单价，只来自 UsageCall 记录，永远标注 ESTIMATE；
  2. 缓存输入折扣（cached input）**从不应用**——系统观察不到哪些字节命中缓存，所以算出的永远是**成本上界**；
  3. 无价格行的模型渲染 UNPRICED，绝不猜价、绝不当 $0；重试是真实行、真实成本。

### 2.2 注册表当前单价（$/1M tokens）【已实现，但标注 UNVERIFIED】

来自 `registry.ts` 种子值（可被环境变量覆盖），按输入价排序：

| 输入价 | 输出价 | 备注 |
|---|---|---|
| $0.15 | $0.60 | 最便宜档 |
| $0.20 | $1.10 | |

| $0.30 | $1.65 | |
| $0.30 | $2.50 | |
| $0.55 | $2.19 | |

⚠️ 这些默认值**未从供应商文档核实**（代码自标 UNVERIFIED）。定价落地前第一步：逐行核对官方价格页并更新 `PRICING_VERSION`。

### 2.3 单任务成本估算示例【设计建议·算例，非实测】

假设一次"章节草稿"调用：输入 20,000 tokens（上下文快照）+ 输出 4,000 tokens（约 3000 字中文正文）：

| 模型档 | 计算 | USD 上界 | 折合 credits |
|---|---|---|---|
| 便宜档 ($0.15/$0.60) | (20000×0.15 + 4000×0.60)/1M | $0.0054 | 6 |
| 中档 ($0.55/$2.19) | (20000×0.55 + 4000×2.19)/1M | $0.0198 | 20 |
| 贵档 ($3.00/$15.00) | (20000×3.00 + 4000×15.00)/1M | $0.1200 | 120 |

**关键洞察**：同一任务在不同模型下成本差 20 倍。这正是积分抽象层的价值——用户只看到"这次草稿花了 N 积分"，你在后台换模型、调路由，不需要重新定价。

一次完整 Agent 运行（规划 + 写作 + 评审 + 记忆投影，多轮多角色）通常是单任务的 5–15 倍消耗【设计建议·定性判断，需用 UsageCall 实测校准】。

## 3. Credit 层：积分怎么算

### 3.1 已实现的换算与扣费机制【已实现】

- **锚定规则**：`1 credit = $0.001 实测 AI 成本`（`CREDITS_USD_PER_CREDIT = 0.001`，charge.ts:53）
- **换算**：`credits = max(1, ceil(USD上界 ÷ 0.001))`；零实测 = 0 积分
- **预扣-结算**：
  - `beginCharge()` 按调用面（surface）预扣保守额度；
  - `settleCharge()` 用实测成本替换预扣：多退少补；
  - **D13 规则：绝不拒绝有余额的用户**——软性调用面 `hold = min(预扣额, 余额)`，只有 1 积分也服务；
  - 硬性调用面（HARD）余额不足则拒绝（402 insufficient_credits）；
  - 未知 surface 取最大预扣额（fail-safe）。
- **成本闸**：每日免费额度 `CREDITS_DAILY_FREE`（默认 20，线上 60）；全局日消费上限触发 kill-switch → 429；管理员豁免。

### 3.2 这套机制对照 ai-pricing 技能的评价

| 技能原则【外部基准】 | Novara 现状 | 判定 |
|---|---|---|
| 积分掩盖 token 经济，换模型不用重新定价 | 1 credit 锚定 $0.001 成本，模型价格可 env 覆盖 | ✅ 符合 |
| 多任务类型不同成本 → 用积分 | 草稿/评审/记忆投影成本各异，按实测统一换算 | ✅ 符合 |
| 按任务复杂度分级（1/3/10 积分） | 按实测成本连续计价，比固定分级更精确 | ✅ 更优 |
| 用户怕不可预测账单 → 加上限与提醒 | 有每日额度与全局熔断，但**无用户侧消费提醒/月度封顶** | ⚠️ 缺 |

### 3.3 需要补的设计【设计建议】

1. **积分来源分账**：免费额度 / 套餐月度额度 / 购买的超量包，三类来源在 CreditLedger 里区分（退款、过期、扣减顺序都要按来源定规则）。建议扣减顺序：免费 → 套餐 → 超量包（先消耗会过期的）。
2. **套餐额度按月发放**：订阅生效时发放当月积分，周期日重置；未用完是否结转（建议：套餐积分不结转，超量包积分 12 个月有效）。
3. **消费提醒**：余额低于 20% / 单次运行预估超过阈值时提示（`context-estimate` 端点已有预估能力，可复用）。
4. **每日免费额度与套餐的关系**：付费用户取消每日免费额度（已含在月度额度里），避免双轨口径混乱；Free 用户保留每日 20（或改为月度 600，口径统一）。

## 4. Plan 层：套餐怎么设计

### 4.1 两份技能合并后的设计框架

**pricing-strategy 的三轴顺序（先度量、再包装、最后定价）**：

```
VALUE METRIC（按什么收费）→ PACKAGING（每档含什么）→ PRICE POINT（收多少）
```

**ai-pricing 的原型判定**：Novara = Copilot（人在环内审批，价值单位是被增强的作者）→ 按人订阅；目标毛利 70–80%【外部基准】。Agent 能力（全自动运行）作为高档权益而非独立计费，避免"按成果收费"承担全部成本波动风险。

**价值度量四问（pricing-strategy）**：
1. 客户为什么愿意多付钱？→ 更多 AI 产出（积分）+ 完整团队 + 多项目
2. 度量随客户成功增长吗？→ 是：写得越多，积分消耗越多，升级动力越强
3. 容易理解吗？→ "积分"需要教育成本，用"约等于 N 万字草稿"做宣传换算
4. 容易被绕过吗？→ 积分服务端计量（已实现），不可绕过 ✅

### 4.2 现有三档的评价与修订建议

现状【已实现·仅展示】：Free $0 / Creator $19 / Studio $49，年付 = 10 个月价（约 17% off）。

| 维度 | 现状 | 技能基准【外部基准】 | 建议【设计建议】 |
|---|---|---|---|
| 档位结构 | 3 档 + Free | Good-Better-Best，中间档 2–3× 入门档 | ✅ 保留；$19→$49 为 2.6×，符合 |
| 年付折扣 | ≈17% | 15–25% | ✅ 保留 |
| 计量单位 | 月 AI 字数（10k/100k/400k） | 积分抽象层 | 🔧 改为月含积分，字数仅作宣传换算 |
| 超量机制 | 无（硬封顶） | 超量 = 成本 1.2–2× | 🔧 加积分超量包 |
| 入门档定位 | Free 即入门 | 入门档应至少覆盖成本 | ⚠️ Free 是获客策略不是档位；Creator 承担入门角色 |
| 顶档企业需求 | Studio 封顶 | SSO/审计/SLA/专属支持 | 🔧 预留 Studio+ 或 Contact us（有 >$1k MRR 客户时再做） |

### 4.3 套餐含积分额度：怎么算出来【设计建议·完整算例】

**公式**：`月含积分 = 月费 × 目标收入占比 ÷ 每积分售价`，且必须满足 `月含积分 × $0.001 ≤ 月费 × (1 − 目标毛利率)`。

以 Creator $19、目标毛利 75%【外部基准：copilot 70–80%】为例：

```
成本预算上限 = $19 × (1 − 0.75) = $4.75/月
→ 月含积分上限 = 4.75 ÷ 0.001 = 4,750 积分
取整建议：4,000 积分/月（留 16% 安全边际，覆盖重试与上界估计误差）
```

同法推三档（目标毛利 75%，含积分取整）：

| 档位 | 月费 | 成本预算(25%) | 建议月含积分 | 宣传换算* | 超量单价建议 |
|---|---|---|---|---|---|
| Free | $0 | 获客成本，单独预算 | 600/月（=每日20×30） | ≈4–6 万字草稿 | 不可购买（升级引导） |
| Creator | $19 | $4.75 | 4,000 | ≈30–40 万字草稿 | $0.0015/积分（1.5×成本） |
| Studio | $49 | $12.25 | 10,000 | ≈80–100 万字草稿 | $0.0012/积分（1.2×成本） |

*宣传换算按"中档模型草稿任务 ≈ 20 积分/3000 字"估算【设计建议·算例】，即 1 积分 ≈ 150 字；**实际换算必须用 UsageCall 实测数据校准后再上定价页**。

**档间递增校验**：600 → 4,000 → 10,000（6.7× / 2.5×）。ai-pricing 建议每档 3–5×【外部基准】，Free→Creator 跨度偏大但符合 freemium 惯例；Creator→Studio 2.5× 略低于建议，可考虑 Studio 提到 12,000（成本 $12，毛利 75.5%，仍达标）。

**超量包定价校验**：$0.0015/积分 = 成本的 1.5×，落在技能建议的 1.2–2× 区间【外部基准】；Studio 超量更便宜，制造升级动力。

### 4.4 功能权益分层（包装轴）【设计建议】

沿用现有配置并按"功能门禁"强化（现在这些限制只在文案里，代码未强制）：

| 权益 | Free | Creator | Studio | 强制执行点（代码位置） |
|---|---|---|---|---|
| 项目数 | 1 | 5 | 不限 | `POST /api/novels` 创建处 |
| Agent 团队 | core（写+编） | 全 5 角色 | 全 5 角色 | runtime 角色调度处（MEMBER_TOOLS 之上加套餐闸） |
| 连续性检查 | ✗ | ✓ | ✓ + doctor | finalize 门禁处 |
| 导出格式 | JSON | +Markdown | +TXT | export 路由 |
| 任务队列优先级 | 普通 | 优先 | 最高 | runs 启动排队处 |
| 支持 | 社区 | 邮件 | 优先 | 非代码 |

### 4.5 定价数字的验证（价格点轴）【设计建议·方法论】

两份技能一致强调：**价格不是成本加成，是定位**。$19/$49 目前只是假设，上线前用以下方法验证：

1. **次优替代锚定**（pricing-strategy）：目标作者现在用什么？通用 AI 聊天工具订阅（约 $20/月档）+ 手动管理连续性。Novara 的差异化 = 结构化记忆 + 五角色流水线，定价应落在"替代成本"与"感知价值"之间。
2. **价值定价启发式**：定价 ≈ 可证实交付价值的 10–20%【外部基准】。对职业作者：节省的整理/续写时间 × 时薪，需要用户访谈数据。
3. **Van Westendorp 四问**（n≥30 目标用户）：太便宜到怀疑质量 / 划算 / 有点贵但可接受 / 贵到不考虑——画曲线找可接受区间与最优点。
4. **转化率信号**：上线后 trial→paid >40% 说明定价偏低（测试涨 20–30%）；15–30% 健康；<10% 先查漏斗再怀疑价格【外部基准】。
